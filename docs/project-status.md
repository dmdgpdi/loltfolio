# 현재 진행 상황과 다음 작업

기준일: 2026-11-27. 완료 이력 대신 현재 상태와 다음 작업을 유지한다.

## 구현 완료

- Riot ID 검증·PUUID 조회, 최근 최대 20경기 수집·저장·부분 성공·완료 표본 보존.
- 19개 분석의 타입·순수 계산·검증·동결·테스트와 저장 경기 → DTO → `GET /api/analysis` 연결.
- 비동기 수집 1~5단계: 작업 도메인·수집 연결·DB 저장소·접수/상태 HTTP API와 순차 워커·Composition, 로컬 복구·종료 검증까지 완료했다.
- 프로젝트 전체 부모 상대경로 import는 Biome `noRestrictedImports`로 금지하고 `@/…`로 통일했다. `./`는 허용하며 Vitest 별칭도 설정했다. 설치 버전에서 `require()`·mock 호출은 검사하지 않는다.

화면은 `Home`이 null을 반환하는 초기 상태다. 최초 생성·최신화 Command와 상태 HTTP API는 구현했고 검색·화면 연결은 미구현이다.

## 유지할 경계

- Domain은 비즈니스 규칙, Application은 유스케이스, Infrastructure는 DB·외부 API를 담당한다. Presentation은 HTTP 변환, Composition은 실제 구현체 조립이다. Controller·서비스는 인프라를 직접 생성하지 않는다.
- 분석 도메인은 match·DB·HTTP에 의존하지 않는다. match의 공개 Application Reader를 분석 Adapter에서 사용한다.
- Query는 저장 경기를 읽고 순수 계산한 DTO만 반환한다. Riot 수집·저장·자동 생성은 Command로 분리한다. 분석 결과 스냅샷은 저장하지 않는다.
- 실제 0·false, 미제공, 판별 불가, 입력 오류를 구분한다. 계산은 지표별 유효 표본 1경기부터 허용하며 표본 수를 보존한다.

## 다음 작업 순서

1. [비동기 수집의 6단계 구현 계획](match-collection-jobs.md#구현-순서와-spec)의 1~5단계는 완료했다. 다음은 6단계의 워커 배포 장소·운영 설정·종료 유예·작업 보관 기간 결정과 실제 환경 검증, 검색·폴링·실패 안내 화면 연결이다.
2. 수집 성공 후 분석 실패 시 재수집 없이 Query로 재분석하는 흐름을 연결한다. 수집 성공과 분석 성공을 구분한다.
3. 초기 카드·표시 단위·반올림·노출 기준을 정하고 검색·결과·최신화 화면을 연결한다. 보류한 챔피언 역할 분류·임의 임계값은 추가하지 않는다.
4. 공개 범위에 맞춰 Riot 전역 호출량 제어·기존 불완전 기록 보완을 별도 설계한다. 플레이어 저장·Riot ID 변경 대응은 필요한 유스케이스가 확인되면 정한다.

## 환경과 검증

- 완료 ID 컬럼 마이그레이션은 생성·검토했고 로컬 임시 스키마에서 검증했다. 작업 테이블·활성 작업 연결 마이그레이션도 생성·검토하고 로컬 임시 스키마에서 검증했다. **두 마이그레이션 모두 앱 DB에는 미적용**이다. 대상 환경 적용 후 실제 저장 데이터의 HTTP 조회를 확인해야 한다.
- 백엔드 spec은 기본 사용법 → 주요 규칙 → 경계·오류 순서다. 타입 검사·fmt·lint와 일반 테스트 937개 통과. DB 테스트 36개는 별도 로컬 PostgreSQL 임시 스키마에서 통과했으며 작업 저장소와 실제 Route 접수 → 워커 → 분석 Query, 독립 프로세스 SIGINT/SIGTERM 종료를 포함한다. 검증 이력은 [경기 수집과 저장](match-data.md)을 따른다.
- 워커는 `pnpm run worker:match-collection`으로 웹과 별도로 실행한다. 웹·워커는 [공통 설정](../src/backend/match/config.ts)을 사용하며 개발·운영 값을 분리하지 않는다. 테스트는 필요한 값을 주입한다. 실제 Riot 호출과 운영 DB·배포 검증은 남아 있다.
- TypeScript·Webpack 프로덕션 빌드와 로컬 HTTP 400/no-store 검증 통과. 기본 Turbopack 빌드는 CSS 처리 중 내부 포트 바인딩 EPERM으로 실패했다. 설정은 변경하지 않았다.
