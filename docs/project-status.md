# 현재 진행 상황과 다음 작업

기준일: 2026-11-06. 현재 코드와 기존 설계 논의를 대조한 작업 안내다. 아래의 예정 작업은 구현 완료나 정책 확정을 의미하지 않는다. 관련 기능이 변경되면 이 문서도 갱신한다.

## 서비스 목표와 책임

Riot ID의 이름과 태그로 플레이어를 찾고, 최근 최대 20개 경기 ID에서 확보한 플레이어 기록을 집계하여 플레이 성향을 보여준다.

- `player`: Riot ID 검증과 PUUID 식별.
- `match`: 플레이어·큐별 경기 수집, 저장, 수집 상태 관리.
- `analysis`: 의사소통·시야·철거 성향 도메인 구현. 나머지 콘텐츠 집계와 검색·최신화 유스케이스는 미구현.
- `src/app`: 얇은 페이지와 HTTP 진입점. 화면 구현은 `src/frontend`에 둔다.

분석 기능은 `player`, `match`의 공개 Application 기능을 사용한다. 두 모듈이 분석 구현을 역참조하지 않는다. Command/Query 구분을 위해 별도 저장소나 Handler를 미리 만들 필요는 없다.

## 현재 구현 범위

| 영역 | 구현 상태와 경계 |
| --- | --- |
| 플레이어 | `RiotId`, `Player`, `PlayerLookupService`, Riot 계정 Adapter와 오류 처리 구현. 플레이어 DB 저장은 없음 |
| 경기 수집 | 최신 ID 최대 20개를 한 번 조회하고 DB 기록 재사용. 없는 경기만 최대 2개씩 병렬 조회 |
| 경기 데이터 | 대상 플레이어의 기본 정보와 핑·시야·전투·라인전·정글·오브젝트·생존·지원 통계 매핑 |
| Timeline | 10분·15분 본인 표본과 동일 포지션 상대 차이 추출 |
| 값의 상태 | `Stat<T>`로 실제 값, `NOT_PROVIDED`, `UNKNOWN` 구분 |
| 영속화 | 경기·수집 상태 Repository 구현과 마이그레이션 존재. 실제 DB 적용 여부는 환경별 확인 필요 |
| 수집 제어 | 원자적 시작, 전체·부분 성공 후 20분 제한, 실패 기록, 429 재시도 시각 보존 |
| 분석 | `CommunicationStyle`의 핑 7종, `VisionStyle`의 와드 행동, `StructureStyle`의 구조물·첫 포탑 관여와 표본 상태 구현. 나머지 콘텐츠·포지션 분포·결과 저장 미구현 |
| 사용자 기능 | 검색·최신화 전체 유스케이스, Controller, Route Handler 미구현 |
| 화면 | `Home`이 `null`을 반환하는 초기 상태 |

구현의 출발점은 [플레이어 조회](../src/backend/player/application/PlayerLookupService.ts), [경기 수집](../src/backend/match/application/MatchCollectionService.ts), [통계 타입](../src/backend/match/domain/types/PlayerMatchStats.type.ts), [통계 매핑](../src/backend/match/infrastructure/riot/toPlayerMatchStats.ts)이다. 상세 수집 정책과 검증 방법은 [경기 수집과 저장](match-data.md)을 따른다.

## 기존 설계와 현재 정책의 차이

- 초기 DDD 문서는 부분 실패 시 성공 시각을 갱신하지 않는 방향이었다. 현재는 확보한 성공분을 저장하고 `PARTIALLY_SUCCEEDED`에도 성공 시각 갱신과 20분 제한을 적용한다.
- 기존 설계의 검색 요구는 저장된 분석 결과가 있으면 자동 수집 없이 반환하고, 없으면 최초 수집·분석하는 것이다. 명시적 최신화는 별도 요청으로 구분한다. 이 전체 흐름은 아직 구현되지 않았다.
- 현재 [경기 수집과 저장](match-data.md)은 리포트 Entity를 추가하지 않고 저장된 경기로 집계하도록 정한다. Entity를 두지 않는 결정만으로 결과 스냅샷의 저장 여부까지 확정되지는 않는다. 기존 리포트 재사용 요구와 결과 계산·저장 방식을 분석 구현 전에 정리한다.
- `GetOrCreatePlayStyleCommand`, `RefreshPlayStyleCommand`는 기존 논의의 권장 메시지다. HTTP 경로·메서드·응답 계약은 미확정이다.

## 남은 작업과 권장 순서

진행 순서는 도메인 모델 → 비즈니스 로직과 테스트 → Repository 인터페이스 → Application Service다. 현재 [CommunicationStyle](../src/backend/analysis/domain/CommunicationStyle.ts)의 핑 사용량과 [VisionStyle](../src/backend/analysis/domain/VisionStyle.ts)의 와드 행동·미구매 경기 수, [StructureStyle](../src/backend/analysis/domain/StructureStyle.ts)의 철거·첫 포탑 관여를 구현했다. 기존 `AnalysisSample`은 제거했으며, 분석 도메인은 `match` 내부에 직접 의존하지 않는다. 다음은 미정인 핑 비교 범위를 확정하고 나머지 스타일의 의미와 계산 규칙을 모델링하는 단계다. Repository와 Service는 아직 추가하지 않았다.

### 1. 분석 범위와 계산 규칙 확정

가장 먼저 진행할 작업이다. 콘텐츠 제안 전체를 한꺼번에 구현하지 않는다.

카드별 표시 항목과 계산 후보는 [플레이 성향 분석 콘텐츠](analysis-content.md)를 기준으로 검토하고 갱신한다.

- 초기 카드와 각 카드의 핵심 수치·보조 수치·설명을 선택한다. 기존 우선 후보는 의사소통, 시야, 정글, 최초 관여, 라인전, 솔로킬, 철거, 승패 비교다. 탱킹·CC·회복 등은 추가 후보이며 출시 범위는 미확정이다.
- 카드별 원천 필드, 단위, 합계·평균·비율 계산식과 표본 필터를 명시한다.
- 지표별 AVAILABLE 표본 수를 사용한다. 여러 필드를 조합하는 지표는 필요한 값이 모두 확보된 표본의 기준을 정한다. 미제공·판별 불가를 0으로 바꾸지 않는다.
- 0경기, 표본 부족, 승리 또는 패배 표본 없음, 비율의 분모 0, 반올림과 표시 자릿수의 처리를 정한다.
- 정글·포지션별 카드에는 실제 집계 대상 경기 수를 표시한다. 확보한 유효 경기 수가 20개 미만이어도 20경기로 표기하지 않는다.
- 포지션별 경기 수와 NONE·NOT_PROVIDED·UNKNOWN 경기 수를 분석 결과에 포함한다. 정글 등 포지션별 카드의 노출 판단에 사용하며, 최소 경기 수와 최종 노출 규칙은 미정이다. 경기별 포지션과 통계의 제공 상태는 향후 세분화된 분석을 위해 계속 보존한다.
- 핑 묶음의 합산 기준을 정한다. 현재 별도로 보존하는 유사 필드를 임의로 합치지 않는다. 탱킹·정글 등 유사 지표의 의미와 단위도 저장 정책을 따른다.
- 분석 결과를 요청마다 계산할지, 스냅샷으로 저장할지와 검색 시 재사용 방식을 정한다.

### 2. 저장 경기 조회와 분석 구현

- 플레이어·큐별 분석 입력 조회 계약을 추가한다. 현재 Repository는 ID 목록 조회와 저장만 지원한다.
- 최신 표본의 선정 기준을 정한다. 저장된 과거 기록으로 제외·실패분을 채워 원래 최신 ID 범위를 벗어나지 않도록, 수집 결과와 일반 조회의 입력 범위를 명시한다.
- 확정한 입출력과 계산 규칙으로 테스트를 먼저 작성하고, DB·HTTP에 의존하지 않는 집계를 구현한다.
- 결과 저장을 선택했다면 새 계산·저장 실패 시 기존 성공 결과를 보존하는 절차를 구현한다.

### 3. 검색·최신화 유스케이스와 API

- 플레이어 식별, 기존 결과 반환 또는 최초 생성, 명시적 최신화를 조율한다.
- 큐 선택, 응답 DTO, 오류 코드, 재시도 가능 시각, 부분 성공 안내를 정의한다.
- 동기·비동기 처리, 최초 생성 동시 요청, 제한 중 기존 결과 반환 여부, 결과가 없을 때 최신화 요청의 처리를 정한다.
- 수집 성공 후 분석만 실패한 경우 수집 없이 재분석할 경로를 정한다. 수집 성공과 분석 성공을 같은 상태로 표현하지 않는다.
- 플레이어 저장과 Riot ID 변경 대응은 필요한 유스케이스가 확인될 때 범위를 정한다.

### 4. 프론트엔드 연결

- Riot ID 검색, 결과 카드, 최신화와 재시도 가능 시각을 구현한다.
- 로딩·오류·빈 결과·표본 부족·부분 성공 표시를 정의한다.
- Model·ViewModel·View 책임은 프론트엔드 지침을 따른다.

### 5. 운영 보완

- 프로세스 종료 후 남은 `IN_PROGRESS` 복구 정책을 정하고 구현한다.
- Riot 전체 호출량 제어가 필요하다. 현재 동시 조회 2개 제한은 전역 rate limit 보장이 아니다.
- 기존 불완전 기록 보완이 필요하면 별도 배치로 설계한다. 현재 수집에 자동 보완을 추가하지 않는다.

운영 보완의 적용 시점은 서비스 공개 범위에 맞춰 결정한다.

## match 린트 정리 완료

2026-11-07에 `complexity` 규칙의 경고 2개·정보 10개를 동작 보존 리팩터링으로 해결했다. 린트 규칙과 한도는 변경하지 않았다.

- `PlayerMatch`의 값 동결·기본 상태 처리와 Timeline 정규화를 분리했다.
- 기본 통계 생성과 Riot 통계 매핑을 기존 관심사별 함수로 나눴다.
- Timeline 파서의 프레임 선택·참가자 검증·상대 비교를 분리하고, 식별 정보와 경기 시간을 입력 객체로 묶었다. 유일한 호출자인 경기 파서도 함께 갱신했다.
- 경기 파서는 참가자 선택·경기 시간 변환·도메인 조립으로 나누고, 분류 검증 조건식과 테스트 반복문을 정리했다.
- DB 통합 테스트는 준비 절차와 테스트 등록 함수를 분리했다. 임시 스키마의 생성·초기화·삭제 정책과 검증 내용은 유지했다.

검증: fmt·lint·TypeScript 검사 통과, lint 진단 없음. 일반 테스트 413개와 별도 로컬 PostgreSQL 임시 스키마의 DB 통합 테스트 9개가 통과했다. Timeline 5초 허용 경계·동률 프레임 선택·본인 프레임 누락 시 처리의 회귀 테스트 6개를 추가했다. DB 스키마와 마이그레이션은 변경하지 않았다.

## 작업 진행 지침

1. 작업 대상의 현재 코드와 관련 문서를 확인한다. 제안·미결정 항목을 확정 정책으로 취급하지 않는다.
2. 동작을 바꾸기 전에 입력·출력·상태·오류·경계 조건을 정리한다. 계산식과 제품 정책의 미결정 부분은 사용자와 합의한다.
3. Backend 지침에 따라 계약과 동작 테스트를 먼저 정의하고 필요한 최소 구현을 진행한다.
4. 완료한 기능과 새로 확정한 정책을 이 문서 및 관련 상세 문서에 반영한다.
5. 루트 `AGENTS.md`의 fmt → lint → test 순서로 검증하고, 환경 때문에 건너뛴 검증은 구분해서 보고한다.
